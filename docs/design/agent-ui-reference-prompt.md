## 一、两张图的视觉语言

### 1. 整体风格

这是一个让内容占主导的浅色 Agent 工作界面。大面积近白背景、深灰正文、中灰过程说明、浅灰用户气泡、很细的边框，以及少量线性图标构成主要视觉元素。整体偏中性，只有轻微暖感，不是明显的米黄纸张风格。

信息层级主要由位置、字号、字重、间距和是否展开来表达。正文不套消息卡片，不使用彩色头像、不反复显示模型名称，也没有贯穿页面的装饰性时间轴。圆角用于真正有边界的对象：用户消息、工具详情、右栏模块和输入框。正文之间没有一道道分隔线。

颜色只在必要处出现：代码语法高亮、错误小图标、变更增减数字、上下文占用分类、小型运行指示器。不能把这些零星色彩扩大为整页主题色。

### 2. 桌面整体布局

图 B 大致是左侧历史栏、中央对话区、右侧检查面板三栏。左栏约占窗口 18%–19%，右栏约占 19%，中间约占 62%；这只是截图比例，真实实现应按固定侧栏和弹性主区域处理。

- 左栏：近白偏灰底色，右边一条极淡分隔线。顶部有系统窗口控件和两个小工具图标，其下是双项分段切换。导航采用图标加文字，留白充足。项目名是浅灰小字，右侧一个加号。会话列表是一行一个条目，选中行用浅灰底和小圆角，不用醒目色带。长标题截断，部分条目尾部有警告图标或小圆点。底部账户区用细线隔开。
- 顶栏：高度很紧凑，左侧为当前会话标题与下拉箭头，标题单行截断；右侧是一排低对比度线性工具图标，选中的图标有浅灰方形底。
- 中间：阅读列明显比整个中央区域窄，图 B 中正文约从 x=417 到 x=1180，宽约 760 个截图像素；正文、工具摘要、工具展开框、输入区左缘基本相互对齐。整体保留宽松的外侧留白。
- 右栏：多个独立白色细边圆角模块纵向排列，模块间距约 8–12 个截图像素。顺序为项目/分支、Context、Connectors、Outputs、Changes、Background tasks。标题左对齐，状态或计数右对齐。

这里的三栏是桌面应用外壳。AShareSim 当前是手机应用，应迁移中央对话的设计语言，并将侧栏职责映射到会话列表和详情面板；不应把三栏等比缩小塞进手机。

### 3. 中央对话：图 B 的核心

- 用户消息右对齐，浅灰实底，没有描边、尾巴和阴影，圆角适中。气泡按文本自然增长；短消息很短，长消息占据阅读列的大部分宽度。气泡内文字仍是正常深色正文。
- 助手回答直接写在背景上，左对齐，无头像、无气泡、无每条消息的角色标题。多段回答读起来像一篇逐步补充的工作记录。
- 一条浅灰过程摘要之后紧接一段深色正文，再出现下一条过程摘要。工具过程分布在实际发生的位置，构成“做了什么—说明结果—继续做什么”的节奏。
- 折叠摘要示例是 `Ran 7 commands, read actions.ts ›`。大部分文字为次要灰色，关键文件名可以用深色，箭头紧跟文本末尾。它不是一个铺满宽度的按钮，也没有把“展开”二字推到最右边。
- 普通段落字号统一，行距克制；通过约一行以内的段间留白分隔段落。没有夸张标题、巨大行距或每句话一个框。
- 行内代码为浅灰小底色、偏砖红等宽文字，嵌在正文基线中，不另起整块卡片。
- 出错时在正文左缘展示小红色轮廓警告图标和灰色错误标题，下方是 `View details ›`。没有全宽红底警报。图中右侧 `Try again` 是短小的浅灰消息样式；仅凭截图不能确定它是用户消息还是重试按钮，实施时应使用项目真实的重试控件。
- 图 B 顶部还有一条弱化的环境提示，属于桌面工具情境，不迁入股票助手。

### 4. 工具详情：图 A 补充的状态

折叠行展开后，下面出现接近正文宽度的浅边框圆角容器。容器标题 `Bash` 是中灰小标题，普通字重；内部代码区又有一层更紧凑的细边框，代码使用等宽字体和有限的语法色。执行输出放在下面，仍用等宽小字，与输入命令分开。

这是有原因的双层结构：外层表示一次工具执行，内层表示输入代码。普通解释文字不应套同样的两层框。没有命令输入的工具只需要单层详情容器。

图 A 的待办清单也是一个浅边框模块：每行小圆形勾选状态加文字，完成与较弱状态通过灰度区分，没有五颜六色的进度卡片。只有项目真的提供任务计划数据时才适用，不能从回答内容凭空生成“已完成”任务。

### 5. 输入区

输入框位于中央阅读列底部，白色底、浅灰细边框、约 16–20 的圆角，宽度与阅读区域协调。框内左侧是加号，接着是低对比度提示文字，右侧是很小的圆形停止控件。输入框边缘有很轻的浮起感，最多只使用极弱阴影。

桌面模型和权限信息位于输入框下方的轻量辅助行，左、右分别对齐。它们不是一排高对比度的药丸按钮。图 B 底部部分内容被裁切，不能据此推定完整菜单结构。

手机端不照搬桌面快捷键提示和权限文案。保留项目已采用的紧凑两层输入框：上层草稿，下层模型、联网、思考、发送；复现的是统一容器、轻量图标和准确对齐。

### 6. 右侧 Context 的排版细节

Context 标题下面是左侧已使用百分比、右侧 token 数量，再下面是一条非常细的分段进度条。分类列表每行使用小色块、名称、用量、占比四个对齐位置；数值右对齐。部分名称有细虚线下划线，表现为可进一步查看的条目。列表下方是可展开的数量条目和压缩操作。

其他右栏模块遵循同一模式：标题 13–14 左右、常规字重、小箭头；摘要右对齐；展开内容使用文件图标、轻量路径或数字。这里的数字、分类和容量是工具真实数据，不是可复制到 AShareSim 的装饰性样例。

### 7. 可以比参考更好的地方

保持同样的视觉克制，在手机上改进可读性和操作性：正文保持 16sp；可阅读的次要文字比截图略深；小图标具有至少 48dp 触控区域；长工具名自然换行；上滑阅读不被流式输出抢走；错误可以明确重试；用户待确认的交易操作始终可见。不要用新增装饰、大面积品牌色或更多卡片来解释“更好”。

#### A. 范围与优先级

当前项目使用 React Native 0.87、TypeScript、lucide-react-native，当前目标是 Android 手机端。继续使用原有技术栈和真实会话数据。按“布局与信息顺序 → 字体与留白 → 颜色与边框 → 图标与状态”的顺序实施。

本任务中的明确视觉要求优先于旧的 AI 设计文档中冲突的外观要求。已有交易行为、模型配置、搜索、公开处理摘要、来源、操作确认和流式数据完整性仍须保留。交易页、账户页等其他页面不在改版范围。

先读取 `AGENTS.md`（如果存在）、`PRODUCT.md`、`DESIGN.md`、`docs/design/ai-chat-layout.md`、`docs/design/chat-detail-ui-validation.md`，再检查：

- `src/ui/screens/AiScreen.tsx`：消息顺序、导航、输入区、键盘与滚动。

- `src/ui/components/AiOptions.tsx`：模型、搜索、思考选择。
- 对应 `__tests__/ui/` 测试与消息类型定义。

先检查 Git 工作区，保留已有未提交改动。任务书生成时 `src/ui/components/ProposalCard.tsx` 已有用户改动，`.claude/` 也已存在未跟踪文件；实施时以重新检查的状态为准，不覆盖、回滚或混入无关修改。

#### C. 手机页面布局

1. 一条紧凑顶栏、一条纵向消息流、一个底部输入区。页面高度由 flex 布局分配，不使用固定屏幕高度。
2. 顶部安全区单独处理；顶栏内容行最小高度 56dp，大字体可增长。左侧返回/会话入口，中间单行标题，次要上下文最多一行，右侧现有详情/菜单入口。不要增加第二排常驻工具栏。
3. 消息区左右边距各 16dp，顶部 12–16dp，底部 16dp。沿用阅读容器最大宽度 760dp。正文、折叠过程行、工具详情的左缘一致。
4. 输入框左右外边距各 12dp，底部处理系统安全区。输入区参与正常布局，消息区不能重复预留一整块输入区高度。最后一行正文可滚动到输入框上方。
5. 手机不显示左右常驻栏。会话历史复用已有列表入口；上下文、来源、模型服务等复用详情页或底部面板。先核实现有能力，不为模仿右栏新增数据库、后台任务或上下文分类服务。
6. 本次不增加桌面模式。宽屏继续限制阅读列宽度，不把正文无限拉宽。

#### D. 消息外观与顺序——最高优先级

助手文字直接排在页面背景上，不加白色外卡、不加头像、不重复显示“AI 助手/模型名/时间”。模型和用量等辅助信息在一轮结束处集中出现一次，详情默认折叠。

用户消息右对齐，最大宽度为阅读区 90%，浅灰底，圆角 12dp，内边距水平 12dp、垂直 10dp；短消息按内容收缩，不固定占满。用户消息之后与第一段助手内容间隔 20dp。已有附件和页面上下文作为轻量辅助信息，不堆多行标签。

关键改造：当前 `AiScreen.tsx` 先渲染整轮 `ChatProcess`，再渲染全部 `turn.answer`，会让过程堆在前面。应根据实际可用的消息顺序，把过程块放回其所属位置：

    用户消息（右对齐浅灰气泡）

    已调用 2 个工具 ›                 ← 次要灰色摘要，默认折叠
    助手对这次结果的说明……             ← 普通正文

    已调用 3 个工具 ›
    助手后续说明……

    待确认操作卡                       ← 真实操作，直接可见
    最终回答与必要来源入口……

以上文字仅是结构示意，实际状态、数量、标题必须由真实记录产生。不把“调用结束”等同于“成功获取数据”。相邻工具记录可以合并，但遇到助手正文必须停止跨段合并；不能把前后两段中间的工具提到轮首。不要凭空把一句完整回答切成若干假阶段。

先核对 `StoredMessage`、`ToolUi` 与流式数据提供的粒度：

- 有顺序的独立消息按原顺序排；仅有累计快照时去重，不能重复计数。
- 单条消息中若只有聚合字段而无先后信息，保留为一个局部过程块，不捏造细粒度时序。
- 工具卡、记忆确认、导航等只渲染一次，不在新过程块和旧消息渲染器中重复出现。
- 使用稳定的轮次/记录标识管理展开状态；流式临时消息转为已保存消息时，已展开内容不能自动收起。
- 公开摘要继续使用现有 `publicSummary` 等来源约束，不把未标注的协议内部 reasoning 字段当作普通可见正文。

#### E. 折叠摘要与工具详情

折叠行使用 13/20 的次要文字，无背景、无边框。文字和 14dp 箭头相距 4dp，箭头紧跟文字，而不是对齐屏幕最右侧。取消独立的右对齐“展开/收起”标签。收起使用向右箭头，展开使用向下箭头。

整行触控高度至少 48dp，视觉上仍然是轻量文字行；不要在 48dp 触控行上下再各堆 16dp 空白。长摘要允许换行，不能挤掉状态或箭头。正在执行时可显示一个 12–14dp 的小型进度指示器及真实当前动作；完成后停止动画。

展开内容紧随当前摘要行：白色或接近页面的背景，1dp 浅边框，12dp 圆角，12dp 内边距。标题为 13–14sp 常规字重。普通只读查询显示已有输入、输出或真实状态；没有原始输入输出字段就显示已有摘要，不新增假的 JSON。

如果已有可展示的代码/命令输入，将输入放到 8dp 圆角的浅边框内层区域，用等宽字；输出放在下方，间距 8dp。代码区域独立横向滚动，普通文字自然换行。不要把所有工具都包装成 `Bash`。

工具错误直接显示一行简短状态，详情按需展开；真正需要用户确认的操作卡在主消息流可见，不藏在折叠过程里面。展开/收起只影响当前过程块，且保持阅读位置。

#### F. Markdown、错误与操作卡

- 中文标题、段落、加粗、列表、链接、引用、表格和代码继续用现有渲染器，不把正文当作一个纯 Text，也不能直接显示原始 Markdown 标记。
- 行内代码使用等宽文字、浅灰底、砖红字；不强制换行成独立卡片。代码块独立横向滚动。
- 表格使用细边框、浅灰表头、右对齐数值/等宽数字特性；长表格内部横向滚动，不撑宽聊天页面。
- 引用为一条细竖线加缩进文字，正常链接用下划线，引用编号仍可点击。
- 错误为小型红色轮廓图标加清楚的中文摘要，下方提供详情与真实可用的重试操作。不要使用巨大红色卡片，不因错误清空已经生成的正文。
- 操作卡保持金额、标的、校验状态与确认动作清晰，沿用真实审批/执行语义。可以统一边框、圆角和间距，但不得点击即执行、重复执行或为了外观删除必要信息。
- 不新增没有真实数据支撑的任务清单、token 进度条、连接状态或成功数量。

#### G. 输入区：紧凑两层，准确对齐

保留手机两层输入结构。白色统一容器、1dp 边框、18dp 圆角、4dp 内边距。

- 上层草稿：16/24 字体，左边距相对容器外缘为 14dp，最小高度 36dp，最高 132dp，之后内部滚动。占位文案简短，例如“给 AI 助手发消息”。不显示桌面快捷键说明。
- 下层工具栏：模型名称在最左；联网与思考在右侧；发送/停止最右。模型文字与上层草稿左缘完全一致，不能在剩余空间里居中。
- 联网使用 18dp 左右的线性图标，启用状态可用小点或细微颜色变化，不做大色块按钮。思考显示图标和简短当前档位，详细选项在原有选择器内。
- 发送/停止可见圆形直径 32dp，外层触控区至少 48×48dp；所有图标动作都保持有效点击区域，不能只靠小图标尺寸。
- 单行草稿加工具栏的正常字号整体容器高度目标约 88–100dp；这是验证目标，不是硬编码高度。大字体、长输入和窄屏允许自然增高。
- 默认使用同一套 lucide 线性图标，笔画约 1.5–1.75，不混用 emoji、实心彩色图标与线性图标。
- 输入空白时发送呈禁用状态；生成中发送位置切换为停止；停止后保留已收到内容。空对话快捷问题最多三个，有消息后消失。
- 320dp 窄屏或 1.3 倍字体下，必要时工具栏换行；模型留在左侧，发送仍可见。不缩小正文或触控区域来硬塞一行。

#### H. 滚动、键盘与状态

复用并保护现有键盘、安全区及流式机制。键盘弹出后输入框和发送键完全可见，底部不能同时重复计算键盘高度和导航栏 inset。用户在末尾时跟随新正文；用户上滑阅读或主动查看过程时停止自动滚到底部。

距末尾超过现有约 60dp 阈值时，显示右下方返回最新按钮；使用 48dp 触控范围，视觉轻量，不遮住输入区。用户点击后才主动恢复跟随。公开摘要与工具展开状态不能随着每个 token 重建；打开选择器和收起详情也不能把用户拖到末尾。

需要覆盖：空会话、普通回答、生成中、多个工具阶段、详情展开、错误、停止、重试、待确认操作、已执行操作、历史长会话。只为实际支持的状态实现控件，不增加死按钮。

#### I. 禁止偏离

不得把结果做成彩色 AI Dashboard。不得加入紫蓝渐变、玻璃拟态、发光边框、大面积品牌色、巨大欢迎区、每条回答独立卡片、重复的模型横幅、装饰性时间轴、满屏状态胶囊、无数据依据的动画进度。不得机械复制桌面侧栏、窗口红绿灯、终端按钮、分支或权限设置。

“比参考更好”限定为可读性、触控、键盘、滚动稳定性和真实状态表达的提升。外观仍服从参考图。

#### J. 实施与验收

1. 检查实际代码与当前界面，列出需要改动的组件，随后直接实施。保留已符合目标的部分；不要为改版重写 AI 请求、存储或交易引擎。
2. 先统一局部 token 与文字层级，再调整消息和过程顺序，最后修正输入区和交互状态。若现有数据不支持某个细节，采用上述诚实降级并在交付中说明。
3. 针对真正变化的行为补充测试：过程与正文顺序、累计记录去重、工具卡只出现一次、流式落库保持展开、上滑阅读不被抢滚动。不要只写样式常量快照来充当视觉验证。
4. 执行项目适用的 TypeScript、lint 和测试检查；本项目提供 `npm run check`。如果检查失败，区分本次问题与既有问题，如实报告。

6. 至少检查正常手机宽度约 390–430dp、320dp 窄屏、1.3 倍系统字体、键盘展开和多行草稿。检查后恢复设备原设置。
7. 截图覆盖：包含两段正文与两个工具阶段的折叠态、一个展开的工具详情、长 Markdown/表格、输入区及键盘、错误或待确认操作。一个静态短回答不足以验收。

## 三、本项目最容易改偏的三个点

1. **只改颜色，不改过程位置。** 当前代码先整轮汇总过程，再展示回答。参考图的特征在于局部过程和说明相互穿插，必须处理渲染顺序。
2. **把桌面截图缩成手机。** 图片中宽阔的侧栏、窄小的文字和桌面快捷键不适合直接照搬。应该保留视觉语言，手机端使用真实的触控尺寸和键盘布局。
3. **以为再写一次“简洁高级”就够了。** 本任务以具体 token、对齐、组件结构和截图检查为准。没有一段文字能保证任意模型一次完成；参考图、明确规格和实际渲染核对共同降低偏差。
